# Лабораторная работа №6
## Реализация взаимодействия компонентов распределенного приложения по модели Pub/Sub

**Предметная область:** фитнес-центр.  
**Основа:** проект лабораторной работы №5 (TCP-клиент, C# сервер, PostgreSQL Primary/Replica).

## 1. Цель работы

Реализовать взаимодействие компонентов по модели Publish/Subscribe средствами C#, без использования внешнего брокера Kafka, RabbitMQ или ActiveMQ. Publisher публикует события, Broker хранит подписки и маршрутизирует сообщения, Subscriber асинхронно обрабатывают только интересующие их типы событий.

## 2. Архитектура приложения

```text
Client → Server → Publisher → Broker-1
                           ↘ Broker-2

Broker → Logger
       → ScheduleService
       → NotificationService
       → AnalyticsService
```

`Server` выполняет операцию предметной области и после успешного `COMMIT` формирует объект `DomainEvent`. `Publisher` принимает событие и передаёт его кластеру Broker. Broker определяет получателей по типу события и запускает их обработку независимо друг от друга.

В реализации используются следующие компоненты:

- `DomainEvent` — идентификатор события, тип, идентификатор сущности, идентификатор клиента, время создания и дополнительные данные.
- `EventPublisher` — публикация событий и фиксация результата.
- `EventBroker` — подписки, выбор получателей, доставка, обработка ошибок и очередь недоставленных сообщений.
- `PubSubCluster` — два Broker и переключение на резервный Broker при отказе основного.
- `EventSubscriberBase` — общая реализация подписчика, включая искусственную задержку, состояние доступности и счётчик обработанных событий.

## 3. Типы событий

| Тип события | Когда создаётся | EntityId |
|---|---|---|
| `TrainingBooked` | После успешного бронирования тренировки | ID записи на тренировку |
| `TrainingCancelled` | После успешной отмены записи | ID записи на тренировку |
| `MembershipPurchased` | После покупки абонемента и назначения его клиенту | ID абонемента |

Событие описывает уже совершившийся факт. Оно публикуется только после сохранения изменений в базе данных.

## 4. Подписчики

| Подписчик | Получаемые события | Действие |
|---|---|---|
| `Logger` | Все три события | Выводит начало и результат обработки события в журнал |
| `ScheduleService` | `TrainingBooked`, `TrainingCancelled` | Обрабатывает изменения расписания |
| `NotificationService` | Все три события | Имитирует отправку уведомления |
| `AnalyticsService` | Все три события | Считает количество обработанных событий; добавляется во время работы приложения |

Искусственные задержки: Logger — 1 секунда, ScheduleService — 3 секунды, NotificationService — 2 секунды, AnalyticsService — 0,5 секунды.

## 5. Обработка отказов и несколько Broker

Каждый Broker хранит список подписчиков и очередь недоставленных сообщений в памяти. Для одной доставки выполняется до трёх попыток. После трёх неудач сообщение помещается в очередь, а остальные Subscriber продолжают обработку. После восстановления компонента выполняется повторная доставка.

В приложении используются Broker-1 и Broker-2. В штатном режиме Publisher сначала обращается к Broker-1. При его недоступности новое событие направляется через Broker-2. Очереди брокеров независимы.

**Ограничение учебной реализации:** очередь хранится в оперативной памяти и очищается при перезапуске сервера. Это временное хранение для демонстрации механизма, а не долговременное хранилище сообщений.

## 6. Проверки

| Проверка | Ожидаемый результат | Фактический результат |
|---|---|---|
| Регистрация трёх основных Subscriber | Все три отображаются в статусе Pub/Sub | Заполнить после запуска |
| Публикация TrainingBooked | Logger, ScheduleService, NotificationService получают событие | Заполнить после запуска |
| Публикация TrainingCancelled | Получатели, подписанные на этот тип, получают событие | Заполнить после запуска |
| Публикация MembershipPurchased | Logger и NotificationService получают событие; ScheduleService не получает его | Заполнить после запуска |
| Отказ ScheduleService | Остальные подписчики завершают обработку; Broker сохраняет недоставленное сообщение | Заполнить после запуска |
| Повторная доставка | После восстановления ScheduleService сообщение доставляется, очередь очищается | Заполнить после запуска |
| Добавление AnalyticsService | Новый подписчик получает последующие события без изменения Publisher | Заполнить после запуска |
| Отказ Broker-1 | Новые события публикуются через Broker-2 | Заполнить после запуска |
| Несколько клиентов | События разных клиентов обрабатываются сервером независимо | Заполнить после запуска |

Автоматический сценарий запускается командой:

```bash
docker compose --profile test run --build --rm integration-test
```

## 7. Сравнение прямого взаимодействия и Pub/Sub

| Критерий | Прямое взаимодействие | Pub/Sub |
|---|---|---|
| Знания компонентов | Сервер знает конкретные сервисы | Publisher знает Broker, Broker знает подписчиков |
| Маршрутизация | Находится в сервере | Находится в Broker |
| Добавление компонента | Нужно менять сервер и его вызовы | Достаточно зарегистрировать нового Subscriber |
| Отказ одного сервиса | Может повлиять на общий поток вызовов | Broker перехватывает ошибку, остальные подписчики продолжают работу |
| Связанность | Более высокая | Более низкая |

## 8. Контрольные вопросы

**1. Что такое Pub/Sub?**  
Модель взаимодействия, в которой Publisher публикует событие, а подписчики заранее регистрируют интересующие их типы событий. Broker доставляет событие подходящим подписчикам.

**2. Что такое Publisher?**  
Компонент, который принимает сформированное событие и передаёт его Broker. Он не вызывает Subscriber напрямую.

**3. Что такое Broker?**  
Посредник, который принимает события, хранит подписки, выбирает подходящих подписчиков, доставляет им события и обрабатывает ошибки.

**4. Что такое Subscriber?**  
Компонент, который регистрирует подписку на определённые типы событий и обрабатывает полученные сообщения.

**5. Что такое Event?**  
Сообщение о произошедшем факте. В этой работе оно содержит тип события, ID сущности, ID клиента, время создания и дополнительные данные.

**6. Как взаимодействуют Publisher и Broker?**  
Publisher передаёт событие Broker. Broker определяет получателей по типу события и доставляет им сообщение.

**7. Может ли один Subscriber получать несколько типов событий?**  
Да. Например, Logger подписан на `TrainingBooked`, `TrainingCancelled` и `MembershipPurchased`.

**8. Что такое слабая связанность компонентов?**  
Это свойство архитектуры, при котором компонентам не требуется знать внутреннее устройство и конкретный состав других компонентов. В Pub/Sub Publisher не знает конкретных подписчиков.

**9. Почему Publisher не должен напрямую обращаться к Subscriber?**  
Чтобы не зависеть от количества, адресов и реализации подписчиков. Маршрутизацию выполняет Broker, поэтому новые Subscriber можно добавлять независимо от Publisher.

**10. Для чего используется асинхронная обработка событий?**  
Чтобы подписчики могли обрабатывать одно событие независимо и параллельно. Медленная обработка одним подписчиком не блокирует запуск остальных.

**11. Как проверить, что Subscriber не получает событие, на которое он не подписан?**  
Опубликовать событие определённого типа и проверить журнал и счётчик `handled` у подписчиков. Например, ScheduleService подписан на события тренировок и не должен получать `MembershipPurchased`.

**12. Что произойдёт при отсутствии подписчиков на событие?**  
Broker не найдёт получателей, зафиксирует это в журнале и завершит публикацию без доставки.

**13. Что произойдёт, если Broker недоступен?**  
Publisher попробует следующий Broker. Если все брокеры недоступны, публикация завершится ошибкой, которая будет записана в журнал. Уже сохранённая бизнес-операция в БД при этом не отменяется.

**14. Какие преимущества даёт Pub/Sub при добавлении новых компонентов?**  
Новый Subscriber можно зарегистрировать на существующий тип события, не изменяя Publisher и серверную бизнес-логику.

**15. Какие недостатки может иметь Pub/Sub?**  
Сложнее отслеживать полный поток обработки, возможны задержки и повторная доставка, требуется обработка дубликатов и ошибок. В данной учебной реализации очередь в памяти теряется после перезапуска процесса.

**16. Какие проблемы могут возникнуть при большом количестве событий?**  
Очередь может расти быстрее, чем подписчики успевают обрабатывать сообщения; увеличиваются задержки и потребление памяти. Нужны ограничения очередей, масштабирование подписчиков, мониторинг и политика повторных попыток.

## 9. Вывод

В ходе работы реализована модель Pub/Sub для приложения фитнес-центра. Сервер публикует события бронирования, отмены бронирования и покупки абонемента. Broker маршрутизирует их подписчикам, поддерживает асинхронную обработку, фиксирует ошибки, временно хранит недоставленные сообщения и повторяет доставку. Добавлены второй Broker и динамический AnalyticsService. Publisher не зависит от конкретных Subscriber, что демонстрирует слабую связанность компонентов.
