# Лабораторная работа №7

## Реализация выбора лидера и механизма консенсуса в распределённой системе

**Предметная область:** фитнес-центр  
**Технологии:** C#, .NET 8, TCP, PostgreSQL, Docker Compose  
**Основа:** проект лабораторной работы №6

## 1. Цель работы

Изучить базовые принципы согласования состояния между узлами распределённой системы, реализовать выбор лидера, обнаружение отказа узла с помощью heartbeat, повторный выбор лидера и голосование с принятием решения на основе большинства.

## 2. Архитектура и внесённые изменения

Проект ЛР №6 сохранён: TCP-клиент, TCP-сервер, PostgreSQL Primary/Replica, механизм Pub/Sub, Publisher, два Broker и подписчики продолжают работать.

Для ЛР №7 добавлен модуль `Server/Consensus/Consensus.cs`:

- `DistributedNode` — логический узел с уникальным ID, состоянием `AVAILABLE` / `FAILED`, ролью `LEADER` / `FOLLOWER` и настройкой голоса `YES` / `NO`;
- `ConsensusCluster` — содержит пять узлов, выполняет heartbeat-проверки, выбор лидера, повторные выборы и голосование;
- `ConsensusResult` — результат голосования: принятое значение, число голосов `YES` / `NO`, количество доступных узлов и размер большинства;
- `ConsensusService` — предоставляет общий экземпляр кластера серверу и выполняет первоначальный выбор лидера.

В `Server/Program.cs` добавлена инициализация механизма консенсуса при запуске. В `Server/RequestHandler.cs` добавлены TCP-операции для просмотра состояния, выборов, имитации отказа и восстановления узлов, heartbeat, голосования, настройки голоса и сброса кластера. В `Client/Program.cs` добавлены пункты меню 20–27. В `Tests/Program.cs` добавлены unit-тесты.

## 3. Правила работы

В кластере пять узлов: `Node 1`–`Node 5`. При запуске все узлы доступны, имеют роль `FOLLOWER`, а затем выполняется начальный выбор лидера. Лидером становится доступный узел с максимальным идентификатором, поэтому при исходном состоянии лидером является `Node 5`.

Для пяти узлов большинство вычисляется по формуле:

`Majority = floor(NodeCount / 2) + 1 = 3`.

Узел, помеченный как `FAILED`, не отвечает на heartbeat и не участвует в голосовании. Если отказал текущий лидер, запускается повторный выбор. Если доступно менее трёх узлов, новый лидер не назначается.

При голосовании действующий лидер предлагает строковое значение, например `TrainingStatus=Confirmed`. Все доступные узлы, включая лидера, отдают настроенный голос. Значение считается принятым только при наличии не менее трёх голосов `YES`. Равенство голосов или отсутствие кворума не приводит к принятию значения.

## 4. Проверочные эксперименты

| Эксперимент | Доступно узлов | Ожидаемый результат |
|---|---:|---|
| Все узлы доступны | 5 из 5 | Leader = Node 5; консенсус достижим |
| Отказ Node 5 | 4 из 5 | Heartbeat timeout; новый Leader = Node 4; консенсус достижим |
| Отказ Node 5 и Node 4 | 3 из 5 | Новый Leader = Node 3; консенсус достижим при трёх `YES` |
| Отказ Node 5, Node 4 и Node 3 | 2 из 5 | Нет кворума; консенсус невозможен, лидер не назначается |
| Четыре доступных узла, 2 `YES` и 2 `NO` | 4 из 5 | Равное разделение; консенсус не достигнут |

**Фактические результаты необходимо заполнить после запуска проекта.** Сборка и выполнение тестов в рабочем окружении не подтверждены: здесь отсутствуют .NET SDK и Docker CLI.

2. Вычисление большинства, равного трём.
3. Выбор доступного узла с максимальным ID.
4. Наличие ровно одного лидера.
5. Обнаружение отказа Node 5 и выбор Node 4.
6. Достижение консенсуса при четырёх доступных узлах.
7. Отказ от принятия значения при разделении голосов 2:2.
8. Невозможность выбрать лидера и достичь консенсуса при двух доступных узлах.

Интеграционные тесты предыдущих лабораторных сохранены.

## 6. Связь с Paxos, Raft и Zab

Реализация является учебной моделью и не реализует полностью ни один из промышленных алгоритмов.

- **Raft:** наиболее близкая аналогия по ролям Leader/Follower и явной процедуре выбора лидера.
- **Paxos:** решает задачу достижения согласованного значения участниками даже при отказах; в отличие от упрощённой модели, использует роли и фазы предложений/подтверждений.
- **Zab:** протокол атомарной рассылки, применяемый Apache ZooKeeper для согласования состояния и упорядочивания обновлений.

## 7. Ограничения реализации

Node 1–5 реализованы как отдельные логические объекты внутри одного процесса `Server`, а не как пять самостоятельных сетевых процессов. Heartbeat моделируется проверкой состояния узла и записью `ALIVE` / `NO RESPONSE` в журнал. Это упрощённая учебная модель, а не полноценный failure detector. Голос `YES` / `NO` задаётся в интерфейсе для проведения экспериментов. Для промышленной распределённой системы понадобились бы сетевой обмен между узлами, таймауты, защита от split-brain, устойчивое хранение состояния и протокол синхронизации.

## 8. Запуск и демонстрация

1. Запустить сервер и базы данных: `sudo docker compose up -d --build`.
2. Запустить клиент: `dotnet run --project Client/Client.csproj`.
3. Показать состояние узлов (пункт 20) и выполнить выбор лидера (21).
4. Предложить значение (25), получить голоса и показать результат.
5. Отключить Node 5 (22), показать heartbeat timeout и выбор Node 4.
6. Отключить ещё два узла и продемонстрировать невозможность консенсуса без большинства.
7. Настроить голоса YES/NO (26) и показать, что равное разделение не даёт консенсуса.
8. Восстановить исходное состояние (27).
9. Запустить тесты: `sudo docker compose --profile test run --build --rm integration-test`.

## 9. Вывод

В лабораторной работе реализована упрощённая модель распределённого согласования на пяти логических узлах. Система выбирает доступный узел с максимальным ID в качестве лидера, обнаруживает имитацию отказа с помощью heartbeat, выполняет повторный выбор и принимает предложенное значение только при наличии большинства голосов. Эксперименты показывают, что при пяти узлах кворум равен трём: система может принять решение при отказе до двух узлов, но не может достичь консенсуса, если доступны только два узла.
